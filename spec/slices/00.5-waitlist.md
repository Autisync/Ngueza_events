# Slice 00.5 — Waitlist landing page

**Status:** done.
**Ships:** week one, before any of the platform exists.
**Ownership:** agent, with design review.
**Depends on:** 01 (schema).

## Why this is first

Supplier recruitment runs for eight weeks before launch (§33), and during that
window client-side interest has nowhere to go. A single page turns eight weeks
of building in silence into an audience, plus evidence of which categories and
municipalities people actually want — which directs recruitment.

It also changes the recruitment pitch from *"we are building a platform"* to
*"four hundred people in Luanda are waiting, sixty of them looking for a venue
in Talatona."*

## Story

> As someone planning an event in Luanda, I can leave my email and say what I
> am looking for, so that I hear from NGUEZA when it opens.

## Scope

One page. No account, no login, no platform.

- The wedge sentence as the headline.
- Email field, category multi-select, município multi-select.
- An optional "when is your event?" month field.
- Double opt-in: confirmation email, then `status = 'confirmed'`.
- A thank-you state that says what happens next and when.

## Tables

`newsletter_subscribers` (`source = 'waitlist'`), `newsletter_consent_events`,
`categories`, `locations`.

## Acceptance criteria

1. Submitting a valid email creates a row with `status = 'pending'` and a
   `newsletter_consent_events` row with action `subscribed`, carrying the exact
   consent wording shown on the page.
2. No email is sent to the address until the confirmation link is followed.
3. Following the confirmation link sets `status = 'confirmed'`, stamps
   `confirmed_at`, and writes a `confirmed` consent event.
4. Following it a second time is idempotent — no duplicate event, no error page.
5. Submitting an address that already exists does not disclose that it exists,
   and does not create a second row.
6. The unsubscribe link in any email works without signing in, and writes an
   `unsubscribed` consent event.
7. Selected categories and municípios are stored in `interests` as ids, not
   names, so the digest can join on them later.
8. The page scores LCP under 2.5s on throttled 3G at a 390px viewport, and
   ships under 180KB of JavaScript.
9. The page renders and submits correctly with JavaScript disabled.
10. The consent checkbox is not pre-ticked, and is separate from any terms link.

## Verified

Every criterion above is asserted in `tests/integration/waitlist.test.ts`
against a real database and a real outbox, plus a no-JavaScript form POST
checked by hand against the running server.

Two findings worth carrying forward, both about Postgres RLS:

- **`RETURNING` needs a SELECT policy.** anon has none — the list must not
  be readable — so an `INSERT ... RETURNING` fails with a misleading
  *"new row violates row-level security policy"*.
- **`ON CONFLICT` needs one too**, to inspect the conflicting row. The
  subscribe path therefore catches the unique violation (`23505`) instead,
  which keeps the table completely unreadable to visitors.

Both are easy to hit again in later slices. When a write mysteriously
fails RLS, check whether it is trying to read something back.

## Out of scope

Sending the digest. Segmentation UI. Anything requiring an account.
